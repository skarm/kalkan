Go-обёртка над KalkanCrypt. Корневой пакет предоставляет типизированный API поверх нативного `ckalkan` и опциональный Java-бэкенд для хеширования, CMS, XML/WS-Security, ZIP и работы с сертификатами на macOS.

## Совместимость

- Go 1.26+
- Нативный бэкенд: `linux/amd64` с `CGO_ENABLED=1` или `windows/amd64`
- Java-бэкенд: JDK 17+ и JAR Java-провайдера НУЦ РК; проверен на `darwin/arm64` с JDK 17 и 26 и провайдером 0.7.5, без нативной библиотеки и cgo

Нативные тесты CI выполняются с `libkalkancryptwr-64.so.2.0.13`.

Нативный бэкенд возвращает `ErrUnavailable` на `windows/386`, Linux с `CGO_ENABLED=0` и других неподдерживаемых нативных платформах. Для доступных Java-операций на macOS явно выберите Java-бэкенд через `WithJavaProvider`.

SDK доступен на [портале разработчиков НУЦ РК](https://pki.gov.kz/ru/developers/). `WithLibraryPath` принимает абсолютный путь к x64 `.so` или DLL.

## Установка

```sh
go get github.com/skarm/kalkan@latest
```

## macOS: Java-бэкенд

Возьмите `knca_provider_jce_kalkan-0.7.5.jar` из каталога `Java/provider` SDK и установите JDK 17 или новее. JAR поставщика не включён в Go-модуль. `WithJavaProvider` требует абсолютный путь к JAR и не совмещается с `WithLibraryPath`. `WithJavaExecutable` принимает путь или имя исполняемого файла; по умолчанию используется `java` из `PATH`. Нужен именно JDK: небольшой загрузчик компилирует встроенное дерево Java-исходников через стандартный compiler API и запускает worker в той же JVM. Отдельный `javac` или система сборки не требуются.

Общий клиент отвечает за проверку входов, последовательность вызовов и диагностику через контракт [`backend.go`](backend.go). [`backend_native.go`](backend_native.go) владеет восстановлением доверия нативного SDK; [`backend_java.go`](backend_java.go) связывает Java-операции с контекстом запроса и преобразует ошибки. Go-адаптер в `internal/javakalkan` отвечает за IPC, HTTP и чтение файлов с лимитами. [Java-worker](internal/javakalkan/worker/README.md) имеет отдельное дерево исходников; ключи, проверка сертификатов, CMS и XML разделены. Тесты с Java SDK находятся рядом с бэкендом в `internal/javakalkan/*_sdk_test.go`: внешний пакет `javakalkan_test` проверяет публичный API. Тесты без SDK используют внутренний пакет.

Используйте `kalkan.Open` корневого пакета; `ckalkan` и `isolated` сохраняют нативные бэкенды. Пример загружает PKCS#12, вычисляет хеш, создаёт прикреплённую CMS-подпись и проверяет её с явно настроенным доверием к УЦ:

```go
import (
	"context"
	"errors"

	"github.com/skarm/kalkan"
)

func cmsRoundTrip(ctx context.Context, password string, payload []byte) (
	digest *kalkan.Digest, result *kalkan.Verification, err error,
) {
	client, err := kalkan.Open(ctx,
		kalkan.WithJavaProvider("/opt/kalkan/knca_provider_jce_kalkan-0.7.5.jar"),
		kalkan.WithJavaExecutable("java"),
		kalkan.WithTrustedCertificate(kalkan.TrustedCertificate{
			Path: "/opt/kalkan/certs/root.cer", Type: kalkan.CertificateCA,
		}),
		kalkan.WithTrustedCertificate(kalkan.TrustedCertificate{
			Path: "/opt/kalkan/certs/intermediate.cer", Type: kalkan.CertificateIntermediate,
		}),
	)
	if err != nil {
		return nil, nil, err
	}
	defer func() { err = errors.Join(err, client.Close()) }()
	if err = client.LoadKeyStore(ctx, kalkan.KeyStore{
		Type: kalkan.PKCS12, Path: "/opt/kalkan/keys/signing.p12", Password: password,
	}); err != nil {
		return nil, nil, err
	}
	digest, err = client.Hash(ctx, kalkan.HashRequest{
		Algorithm: kalkan.GOST2015_512, Data: kalkan.Bytes(payload),
	})
	if err != nil {
		return nil, nil, err
	}
	signed, err := client.SignCMS(ctx, kalkan.SignCMSRequest{
		Data: kalkan.Bytes(payload), IncludeCertificate: true,
	})
	if err != nil {
		return digest, nil, err
	}
	result, err = client.VerifyCMS(ctx, kalkan.VerifyCMSRequest{
		Signature: kalkan.DER(signed.Data), SignerID: 1,
	})
	return digest, result, err
}
```

С JAR провайдера доступны `Hash` с SHA-256 и тремя алгоритмами ГОСТ, загрузка PKCS#12, `SignCMS`, `SignHash`, `VerifyCMS`, `GetTimeFromSig`, загрузка доверенных сертификатов, `ValidateCertificate`, `GetCertFromCMS`, `X509ExportCertificateFromStore`, `X509CertificateGetInfo` и `X509CertificateGetInfoFields`.

`CertificateInfo.SignatureAlgorithm` использует формат нативного SDK `signatureAlgorithm=<имя>(<OID>)` для известных алгоритмов подписи, включая RSA и ГОСТ. Для неизвестного алгоритма Java-бэкенд возвращает сам OID в точечной записи. Чтение этих метаданных не проверяет подпись сертификата.

CMS можно подписывать с вложенными или отсоединёнными данными и возвращать в DER, Base64 или PEM. Для добавления подписанта передайте CMS из памяти в DER/Base64/PEM через `SignCMSRequest.ExistingSignature`, исходные данные в `Data` и соответствующий контейнеру `Detached`. Перед добавлением проверяются прежние подписи, доверие и отзыв; записи подписантов, сертификаты и CRL сохраняются. Для отсоединённой проверки задайте `Detached: true` и передайте исходные данные в `Data`. `VerifyCMS` проверяет всех основных подписантов; `SignerID` выбирает только сертификат в результате `SignerCert` (`0`: не возвращать, `1`: первый). Данные прикреплённого CMS возвращаются при проверке подписи из памяти; при файловом входе и отсоединённой проверке поле `Data` остаётся пустым. При добавлении подписанта данные в Base64/PEM, включая файлы, декодируются в Go до вызова бэкенда; `WithMaxInputSize` также ограничивает размер этих закодированных файлов.

`Timestamp: true` в `SignCMSRequest` или `SignHashRequest` запрашивает новый токен RFC 3161 по адресу `WithTSAURL` (по умолчанию `http://tsp.pki.gov.kz:80`). Ответ должен соответствовать случайному nonce запроса и SHA-256 от байтов подписи; до включения проверяются подпись TSA, назначение сертификата, цепочка и отзыв. `GetTimeFromSig` подтверждает достоверность штампов первого подписанта и их связь с байтами подписи, возвращая самое раннее подтверждённое время. Метод работает и с отсоединённым CMS без исходных данных; основную подпись документа он не проверяет. Для проверки документа используйте `VerifyCMS`.

Java-проверке CMS нужна цепочка до явно доверенного корневого УЦ; загрузите необходимые для её построения промежуточные сертификаты. По умолчанию проверяются сроки сертификатов. `SkipCertificateTimeCheck` отключает проверку дат, сохраняя проверку цепочки. Это намеренно отличается от более широкого эффекта нативного флага `KC_NOCHECKCERTTIME`; полного совпадения политики валидации не обещается. Пример использует проверку дат по умолчанию; истёкшие PKCS#12 из репозитория требуют явного отключения только в тестах исторических материалов.

`VerifyCMS` по умолчанию проверяет отзыв через OCSP для всех сертификатов цепочки, кроме доверенного корня. Используется адрес из `WithOCSPURL` (по умолчанию `http://ocsp.pki.gov.kz`). Проверяются подпись ответа, полномочия ответчика, идентификатор сертификата и его издателя, актуальность и статус. Отзыв, неизвестный статус, просроченные или поддельные данные и недоступность сервиса приводят к ошибке. Для CRL передайте `WithJavaRevocation(CertificateValidationCRL, source)`: `source` может быть HTTP(S)-адресом, файлом или каталогом с `.crl`, `.der`, `.pem`; пустая строка использует точки распространения из сертификатов. В локальном наборе нужны полные CRL всех издателей цепочки. Для каждого издателя выбирается наиболее новый применимый полный CRL с проверенной подписью и сроком действия: по `CRLNumber`, если номера доступны, иначе по времени выпуска; противоречивые номера или время выпуска отклоняются. Устаревшие CRL в наборе не мешают использовать актуальный CRL с проверенной подписью. CRL загружаются при `Open`; для обновления локального набора откройте новый клиент. `WithJavaRevocation(CertificateValidationNone, "")` явно отключает только отзыв для офлайн-проверок; это отражается в диагностике. `SkipCertificateTimeCheck` проверку отзыва не отключает.

При наличии RFC 3161 `signatureTimeStampToken` проверяются связь штампа с байтами подписи CMS, подпись TSA, ESSCertID/ESSCertIDv2, назначение сертификата TSA, его цепочка и сроки на момент штампа. Отзыв в цепочке TSA проверяется по текущим данным согласно выбранному режиму. Корневые и промежуточные сертификаты TSA также должны быть загружены; они могут отличаться от цепочки подписанта документа. Недоверенный или повреждённый штамп отклоняет весь CMS, даже при `SkipCertificateTimeCheck`. Время штампа не заменяет текущую дату проверки сертификата основного подписанта. Это не архивная проверка статуса отзыва на момент подписания.

Доступен и отдельный `ValidateCertificate` с режимами None, CRL и OCSP; для OCSP можно получить проверенный ответ через `ReturnOCSPResponse`. Явный `CheckTime` в режимах None/CRL проверяет сроки сертификатов и цепочку на заданный момент и имеет приоритет над `SkipCertificateTimeCheck`. CRL должен действовать на этот момент; более поздняя дата отзыва не отклоняет исторический результат. Историческая OCSP-проверка требует архивных ответов и пока не поддерживается. Поддерживаются полные прямые CRL; delta, indirect и scoped CRL отклоняются. Делегированный OCSP-ответчик должен иметь `OCSPSigning` и `id-pkix-ocsp-nocheck`; отсутствие последнего явно не поддерживается. Допустимое расхождение часов — пять минут; ответ OCSP без `nextUpdate` принимается не более 24 часов от `thisUpdate`. Отсутствующий nonce допускается при актуальном подписанном ответе, несовпадающий nonce отклоняется. Контрподписи CMS, вложенные штампы и аппаратные токены остаются неподдерживаемыми. Некоторые неподдерживаемые Java-операции распознаются через `ErrJavaUnsupported`; для методов, отсутствующих у бэкенда, совпадение с этим sentinel не гарантируется. Ошибки провайдера представлены типом `JavaError` и не содержат нативного статус-кода KalkanCrypt.

Хранилище доверия Java не зависит от ключевого контейнера: смена PKCS12 сохраняет доверенные сертификаты без повторного чтения файлов.

Сеть для TSA и проверки отзыва обслуживает Go: `EndpointPolicy` применяется и к URL из сертификатов, перенаправления запрещены, таймаут одного HTTP-запроса — 15 секунд. Ответ после распаковки ограничен 64 MiB или меньшим положительным `WithMaxInputSize`. `WithProxy` задаёт HTTP-прокси с необязательной Basic-аутентификацией для этих запросов, включая HTTPS CONNECT. Переменные окружения HTTP-прокси не используются. По умолчанию URL не ограничены списком хостов; при обработке недоверенных сертификатов задайте `WithEndpointPolicy`.

Для `SignXML`, `VerifyXML`, `SignWSSE`, `GetCertFromXML` и `GetSigAlgFromXML` дополнительно нужны XMLDSig-адаптер Kalkan, Apache Santuario и SLF4J API. Вместе с `WithJavaProvider` передайте абсолютные пути:

```go
kalkan.WithJavaXMLLibraries(
    "/opt/kalkan/java/kalkancrypt-xmldsig-0.5.jar",
    "/opt/kalkan/java/xmlsec-3.0.6.jar",
    "/opt/kalkan/java/slf4j-api-2.0.9.jar",
)
```

Адаптер поддерживает XML-подписание RSA/SHA-256, ГОСТ95 и ГОСТ2015-512; XML-подписание ГОСТ2015-256 в адаптере XMLDSig 0.5 отсутствует. Доступны все шесть режимов каноникализации публичного API. WS-Security подписывает выбранный Body SOAP 1.1/1.2 со ссылкой, использующей exclusive canonicalization, и помещает сертификат X509v3 в `wsse:KeyIdentifier`, как нативный SDK. Проверка и извлечение сертификата также принимают локальные ссылки на BinarySecurityToken. `VerifyXML` проверяет все подписи и применяет ту же политику явного доверия и OCSP/CRL; для SOAP также нужен правильный `ExpectedBodyID`.

XML ID должны быть уникальны во всём документе и содержать только символы XML `NameChar`, кроме двоеточия; числовые ID разрешены для совместимости с нативным SDK. URI-экранирование в ссылках не поддерживается. Разрешены ссылки только на текущий документ или уникальный ID элемента, преобразования enveloped-signature и каноникализации; XPointer, внешние ссылки, XPath/XSLT, `ds:Object`, XAdES и XML-штампы отклоняются. Добавление подписи через `SignXML` возвращает `ErrJavaUnsupported`, если результат нарушает существующую подпись. При проверке её сохранности проверяются подпись и связанные данные, но не доверие и сроки сертификатов прежних подписантов. Извлечение сертификатов и алгоритма возвращает метаданные и не заменяет проверку подписи. Хеширование, CMS и работа с сертификатами доступны и без дополнительных XML JAR.

Каждый Java-клиент владеет постоянным дочерним процессом и обменивается запросами через каналы. Вызовы внутри клиента выполняются последовательно; при работе с разными ключами синхронизируйте всю последовательность загрузки и подписания. Отмена запроса в очереди сохраняет сессию. Отмена после начала запроса к worker завершает Java-сессию; следующие вызовы возвращают `ErrJavaWorkerFailed`, для восстановления нужен новый `Open`. `Close` дожидается завершения процесса и удаляет временные исходники и классы worker. Входы и результаты целиком находятся в памяти; потокового API нет. Файловые входы `Hash`, `SignCMS`, `VerifyCMS` и загрузки доверенных сертификатов должны быть обычными файлами и также ограничиваются `WithMaxInputSize`; контейнеры PKCS12 провайдер загружает отдельно. Файловые входы CMS, ZIP и CRL используют общие проверки отмены и размера; отдельное поле Java-протокола ограничено размером массива со знаковой 32-битной длиной. Go проверяет отмену между чтениями файла, но не может прервать системный вызов файловой системы. `WithMaxOutputBufferSize` ограничивает возвращаемые поля. Эти настройки не ограничивают суммарную память JVM.

## Пакеты

- [`github.com/skarm/kalkan`](https://pkg.go.dev/github.com/skarm/kalkan): типизированный API для CMS, XML, WS-Security, хеширования, ZIP, сертификатов, OCSP/TSA, прокси и логирования
- [`github.com/skarm/kalkan/ckalkan`](https://pkg.go.dev/github.com/skarm/kalkan/ckalkan): ABI-уровень с нативными флагами, кодировками и настройками буферов
- [`github.com/skarm/kalkan/isolated`](isolated): отдельные локальные worker с независимыми сессиями SDK и отменой через завершение процесса

Используйте `ckalkan`, если нужной операции нет в корневом пакете. Также используйте его для собственного высокоуровневого слоя над KalkanCrypt: со своими типами запросов, валидацией, политикой буферов, логированием или преобразованием ошибок.

`ckalkan` близок к нативному API. Вызывающий код отвечает за нативные флаги, кодировки, размеры буферов и обработку статус-кодов; он также должен учитывать жизненный цикл клиента, ограничения ABI и необходимость изоляции процесса.

### Выходные буферы `ckalkan`

Параметры буферов `ckalkan` разделены по двум формам ABI:

- `WithListBufferSize` задаёт начальную аллокацию для `KC_GetTokens` и `KC_GetCertificatesList`; значение по умолчанию равно 1 MiB. В протестированном Linux SDK 2.0.13 эти функции не получают ёмкость буфера в байтах, а `tk_count` и `cert_count` являются выходными счётчиками элементов. Опция управляет размером аллокации, но не ограничивает нативную запись.
- `WithBufferSize` задаёт общую начальную ёмкость для вызовов с выходным буфером, которым передаётся его размер. Поля ёмкости в запросе имеют приоритет над этой опцией. Без неё используются начальные размеры 32 байта для сырых хешей SHA-256, ГОСТ 34.11-95 и ГОСТ 34.11-2015-256; 64 байта для сырого ГОСТ 34.11-2015-512; 256 байт для вывода хеша в Base64/PEM при любом алгоритме; 128 байт для остальных сырых алгоритмов хеша; 4 KiB для метаданных, 8 KiB для сертификатов и 64 KiB для подписей и остальных выходных буферов. Для прикреплённого CMS учитываются размер входных данных в памяти или файла и консервативный запас на подпись; также учитывается расширение Base64 и PEM. Для подписанного XML/WSSE учитываются размер XML в памяти и тот же запас (`KC_IN_FILE` этими двумя вызовами SDK не поддерживается). Перед вызовом ёмкость записывается в выходной параметр длины. При `KCR_BUFFER_TOO_SMALL` обёртка увеличивает буфер и повторяет вызов.
- Каждый выходной буфер по умолчанию имеет жёсткий лимит 64 MiB (`ckalkan.DefaultMaxOutputBufferSize`). `WithMaxBufferSize(0)` восстанавливает безопасное значение по умолчанию; положительное значение осознанно задаёт меньший или больший лимит вплоть до максимума нативного C `int` — 2^31-1 байт. Отрицательное значение приводит к ошибке `ErrInvalidOutputBufferSize` из `New`. Если нативный код сообщает размер выше действующего лимита, обёртка до повторного вызова и аллокации чрезмерной ёмкости возвращает типизированную `OutputBufferLimitError` с названием операции, запрошенным размером и применённым лимитом.

В Linux для `ZipConVerify` нужна защитная аллокация 64 KiB: SDK 2.0.13 может записать данные за пределами меньшей переданной ёмкости. Если явный жёсткий лимит меньше этого безопасного минимума, вызов завершается ошибкой до входа в нативную библиотеку.

Положительные значения `WithBufferSize` и `WithListBufferSize` нормализуются до значения не менее 64 KiB. Положительное значение `WithMaxBufferSize` соблюдается точно до максимума ABI C `int`. Меньший жёсткий лимит может не позволить операции использовать обычную начальную ёмкость; значение 64 MiB по умолчанию является границей безопасности и доступности, а не указанием, что операция обычно должна использовать столько памяти.

Лимит аллокации также ограничивает повторный рост обёртки для `KC_GetTokens` и `KC_GetCertificatesList`, но не устраняет их отдельный ABI-риск: эти две функции не получают ёмкость в байтах, поэтому опция не способна ограничить даже первую нативную запись.

Формально успешный результат списка, который занял всю аллокацию без завершающего NUL, считается потенциально усечённым и повторяется с увеличенной аллокацией.

## Использование клиента

```go
import (
	"context"
	"errors"
	"os"

	"github.com/skarm/kalkan"
)

func hash(ctx context.Context) (digest *kalkan.Digest, err error) {
	client, err := kalkan.Open(ctx,
		kalkan.WithLibraryPath(os.Getenv("KALKANCRYPT_LIBRARY")),
	)
	if err != nil {
		return nil, err
	}
	defer func() {
		err = errors.Join(err, client.Close())
	}()

	return client.Hash(ctx, kalkan.HashRequest{
		Algorithm: kalkan.GOST2015_512,
		Data:      kalkan.Bytes([]byte("document payload")),
	})
}
```

Для нативного бэкенда `Open` по умолчанию настраивает production endpoints:

- TSA: `http://tsp.pki.gov.kz:80`
- OCSP: `http://ocsp.pki.gov.kz`

Соответствующие test endpoints:

- TSA: `http://test.pki.gov.kz/tsp/`
- OCSP: `http://test.pki.gov.kz/ocsp/`

Test endpoints задаются явно:

```go
client, err := kalkan.Open(ctx,
	kalkan.WithLibraryPath(os.Getenv("KALKANCRYPT_LIBRARY")),
	kalkan.WithTSAURL("http://test.pki.gov.kz/tsp/"),
	kalkan.WithOCSPURL("http://test.pki.gov.kz/ocsp/"),
)
```

`WithTSAURL` и `WithOCSPURL` настраиваются независимо. Для операций подписания нужен `LoadKeyStore`; примеры находятся в [`example_test.go`](example_test.go).

`Open` всегда настраивает непустой TSA URL; `WithTSAURL("")` недопустим. Поля `Timestamp` в `SignCMSRequest` и `SignHashRequest` запрашивают штампы времени независимо от этой настройки URL. Функция SDK `KC_TSASetUrl` не возвращает статус, поэтому успешная настройка или вызов `ckalkan.Client.SetTSAURL` не подтверждает принятие URL библиотекой и доступность TSA-сервера.

## Модель выполнения нативного бэкенда

Состояние KalkanCrypt глобально для процесса. Нативные вызовы сериализуются по отдельности. Последовательность `LoadKeyStore` и подписания не атомарна: между ними могут выполниться другие вызовы. При совместном использовании клиента с разными контейнерами ключей необходимо синхронизировать всю последовательность загрузки и подписания или использовать отдельные процессы.

Храните и передавайте указатели, возвращённые `Open` или `ckalkan.New`; не копируйте структуры клиентов. `go vet` обнаруживает случайное копирование, в том числе низкоуровневого `ckalkan.Client`.

После успешного нативного `LoadKeyStore` клиент повторно загружает все сертификаты, успешно загруженные через `WithTrustedCertificate` или `LoadTrustedCertificate`, до допуска следующей операции. Байты сертификатов копируются после первой загрузки и хранятся до `Close`; файлы сертификатов должны оставаться доступными и неизменными для последующих загрузок контейнера. Восстановление завершается даже при отмене контекста после начала нативной загрузки контейнера. Ошибка восстановления сообщает о частичном успехе: контейнер уже сменился, доверие может быть неполным, а следующий `LoadKeyStore` повторит восстановление. Смена контейнера не откатывается.

`context.Context` может отменить ожидание гейта корневого клиента. Он не прерывает ожидание процессного мьютекса низкого уровня, загрузку библиотеки и уже начавшийся вызов KalkanCrypt, включая `Init`. Освобождение ресурсов после неудачного или отменённого `Open` также выполняется без отменяемого ожидания.

`Client.Close()` ждёт активный вызов и может заблокироваться навсегда. `Client.CloseContext(ctx)` прекращает ожидание вызывающего кода по `ctx.Err()`, оставляет клиент в состоянии `closing` и отклоняет новые операции. Жёсткие дедлайны требуют изоляции процесса. Закрытие начинается даже с уже отменённым контекстом. После завершения повторные вызовы возвращают сохранённый результат.

В Windows `LoadLibraryExW` вызывается с `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`. Текущий рабочий каталог и `PATH` исключены. Узкие `char*` аргументы передаются как UTF-8 с завершающим NUL.

## Опциональная изоляция процесса

Импортируйте `github.com/skarm/kalkan/isolated`, чтобы каждый нативный клиент работал в отдельном дочернем процессе. Приложение само предоставляет режим worker в своём исполняемом файле; отдельная команда и сборка worker не нужны. `kalkan.Open` с `WithLibraryPath` сохраняет выполнение в текущем процессе.

В начале `main`, до разбора аргументов приложения и запуска сервисов:

```go
if len(os.Args) == 2 && os.Args[1] == "--kalkan-worker" {
	if err := isolated.RunWorker(context.Background()); err != nil {
		os.Exit(1)
	}
	os.Exit(0)
}
```

Родитель запускает копию собственного исполняемого файла. `WorkerArgs` выбирает ветку выше и передаётся напрямую, без shell. Не запускайте сервисы в `init`: эти функции выполнятся и в дочернем процессе. `RunWorker` перенаправляет стандартные потоки в null; после его возврата нужно сразу завершить процесс, даже при успехе, поскольку нативный вызов ещё может висеть.

В обычной ветке выполнения приложения:

```go
executable, err := os.Executable()
if err != nil {
	return err
}
client, err := isolated.Open(ctx, isolated.Config{
	WorkerPath:  executable,
	WorkerArgs:  []string{"--kalkan-worker"},
	LibraryPath: "/opt/kalkan/libkalkancryptwr-64.so.2.0.13",
})
if err != nil {
	return err
}
defer client.CloseContext(ctx)

digest, err := client.Hash(ctx, kalkan.HashRequest{
	Algorithm: kalkan.SHA256,
	Data:      kalkan.Bytes([]byte("document payload")),
})
```

Один файл `.so`/DLL может использоваться несколькими worker: каждый процесс хранит свои ключи, доверие и изменяемое состояние SDK. Независимые клиенты работают параллельно; внутри общего клиента синхронизируйте составную последовательность загрузки ключа и подписания.

В [полных примерах](isolated/example_test.go) показаны SHA-256 хеширование файла и подпись CMS с проверкой. Каждый включает свою ветку worker, настройки, обработку ошибок и закрытие клиента. Для запуска перенесите нужную функцию в своё приложение как `main` (с `package main` и нужными импортами), измените пути к входному файлу и сертификатам, задайте `KALKANCRYPT_LIBRARY` и соберите приложение на поддерживаемой SDK платформе. Для подписания также задайте `KALKAN_KEY_PASSWORD` и используйте действующий сертификат с его цепочкой CA. Выходной CMS-файл не должен существовать. Отдельный исполняемый файл worker не нужен.

Пакет реализует все 21 операцию корневого клиента с существующими типами запросов и результатов. Настройки библиотеки передаются через `Config`, без сериализации замыканий `kalkan.Option`. `TSAURL` и `OCSPURL` — необязательные указатели: nil выбирает корневое значение по умолчанию. `Logger` и `Observer` выполняются в родителе.

Worker обменивается кадрами через два анонимных канала: бинарный заголовок и следующие за ним сырые блоки данных. Поля операций, настройки, ошибки и наблюдения имеют явный бинарный формат; байтовые входы и результаты передаются напрямую. `kalkan.File(path)` передаёт только путь; родитель не читает файл. Отправитель использует исходные срезы до возврата метода; при отмене он дожидается остановки своей горутины ввода-вывода. До загрузки SDK стандартные потоки перенаправляются в null, поэтому нативный stdout не повреждает ответы. TCP-сокет и токен не используются. Передача сохраняет байты, кодировки, явно пустые источники и произвольные байты строк. Ошибки сохраняют исходный текст и проверки `errors.Is` для sentinel-ошибок пакетов, контекста и `io/fs`. Нативные `ckalkan.KalkanError` и `ckalkan.OutputBufferLimitError` доступны через `errors.As`; `ckalkan.ErrorCodeOf` также работает. Другие конкретные типы ошибок не восстанавливаются.

`Open`, операции и `CloseContext` используют только переданный контекст, без внутренних тайм-аутов. Задавайте срок через `context.WithTimeout` или `context.WithDeadline` либо отменяйте контекст явно; без дедлайна ожидание может быть неограниченным. Контекст операции охватывает ожидание очереди и обмен с worker. Отмена контекста запуска после успешного `Open` не закрывает клиент. Отмена запроса в очереди сохраняет worker; отмена после начала отправки завершает его. Последующие вызовы возвращают `isolated.ErrWorkerFailed`, восстановление требует нового клиента. Автоматического повторения операций нет.

`Close()` ждёт активный вызов и штатное завершение worker без тайм-аута. Отмена любого ожидающего `CloseContext(ctx)` принудительно завершает worker и заканчивает общее закрытие с `ctx.Err()`, в том числе если другая горутина уже вызвала `Close()`. Конкурентные и повторные вызовы закрытия получают сохранённый результат; завершённый результат имеет приоритет над отменой контекста. Для каждого запущенного процесса выполняется ожидание завершения. Контекст не может прервать кодирование, декодирование и пользовательские callbacks в Go. Полученные нативные наблюдения вызываются после освобождения гейта, а наблюдения Close — после публикации результата закрытия, поэтому повторный вход допустим.

IPC не добавляет ограничения на размер сырых данных: длины кадров и блоков передаются 64-битными числами. Получатель читает данные частями ограниченного размера и объединяет их один раз после получения полного блока; маленькие блоки не требуют объединения. Обрезанный кадр не вызывает выделение памяти под весь заявленный размер. Операции по-прежнему принимают и возвращают целые срезы байтов, поэтому это не потоковый API к SDK. Метаданные ограничены 64 KiB, число блоков в кадре — 1024. Настройки входных и выходных лимитов и ограничения SDK продолжают действовать; это не ограничение всей памяти процесса.

Изоляция разделяет память и сессии SDK; worker сохраняет доступ приложения к файловой системе, окружению и сети. Относительные пути используют рабочий каталог worker на момент запуска. Прерванная операция могла уже создать результат или обратиться к TSA. Принудительное завершение пропускает deferred cleanup, поэтому могут остаться выходные файлы или временные ZIP-каталоги; приложение управляет путями результатов и восстановлением. Пароли и IPC-данные копируются в памяти и не могут быть обнулены этим пакетом.

## Входы и лимиты

Операции используют значения `Source`:

- `kalkan.Bytes(data)`: непреобразованные байты в памяти для данных, XML или уже декодированного бинарного объекта; конкретная операция выбирает нативные флаги
- `kalkan.Base64(data)`: вход в памяти, уже содержащий Base64-текст; конструктор не кодирует `data`
- `kalkan.PEM(data)`: готовый PEM-блок; конструктор не создаёт PEM-оболочку
- `kalkan.DER(data)`: готовый DER-объект для явного выбора DER в CMS и операциях с сертификатами
- `kalkan.File(path)`: путь к файлу; поддерживающие его операции передают путь в KalkanCrypt, а `GetCertFromCMS` читает файл в память

Допустимые варианты зависят от операции.

Кодировка источника, отличная от `EncodingAuto`, имеет приоритет над полями кодировки запроса и значениями операции по умолчанию. `Bytes`, `Base64`, `PEM` и `DER` задают явную кодировку; `File` начинает с `EncodingAuto`. Например, `VerifyCMSRequest.Encoding: EncodingBase64` не заставит интерпретировать источник `Bytes` как Base64. Используйте `Base64(encoded)` или явно восстановите выбор кодировки из запроса через `Bytes(encoded).WithEncoding(EncodingAuto)`.

Конструкторы источников в памяти не копируют и не преобразуют переданный срез. Валидация конкретной операции может декодировать PEM или Base64 до нативного вызова. На Linux и Windows входы в памяти с явной длиной обычно передаются в KalkanCrypt напрямую, без копирования в адаптере. Для данных `SignData` в Base64 и CMS-подписей `VerifyData`, `GetCertFromCMS` и `GetTimeFromSig` в Base64 создаётся отдельная копия с завершающим NUL: Linux SDK 2.0.13 читает эти входы как C-строки, несмотря на аргумент длины. Передаваемая SDK логическая длина не меняется. За исключением `GetCertFromCMS`, `File` передаёт исходный путь после проверки на пустое значение и NUL; нативный адаптер добавляет C-string терминатор, необходимый для `KC_IN_FILE`. Не изменяйте заимствованные срезы и файлы до завершения вызова.

Для нативного бэкенда `WithMaxInputSize` ограничивает входы в памяти на уровне корневого API и файлы, читаемые `GetCertFromCMS`. Ограничение не распространяется на файлы, которые нативный SDK читает напрямую, и нативные выходные буферы. Java-бэкенд также применяет его к данным и доверенным сертификатам, читаемым его Go-адаптером; контейнеры PKCS12 этим лимитом не ограничиваются. Для нативных выходных буферов по умолчанию действует жёсткий лимит 64 MiB (`kalkan.DefaultMaxOutputBufferSize`). `WithMaxOutputBufferSize(0)` восстанавливает это значение; положительное значение задаёт меньший или больший лимит (до максимума нативного C `int`), а отрицательное приводит к `ErrInvalidInput` из `Open`. Опция передаётся в `ckalkan.WithMaxBufferSize`. При превышении действующего лимита до чрезмерного повторного вызова или выделения памяти возвращается `ckalkan.OutputBufferLimitError`.

Бинарные результаты возвращаются строго по сообщённому SDK значению `outLen`; нулевые байты внутри этой длины сохраняются. У возвращённого среза `len` и `cap` ограничены логическим результатом, поэтому неиспользованная ёмкость буфера наружу не видна. Результаты-срезы являются ограниченными представлениями, а не копиями: пока результат используется, в памяти остаётся успешная исходная аллокация, зато не создаются вторая большая аллокация и копия. Известные текстовые результаты обрабатываются как C-строки и заканчиваются на первом NUL: некоторые методы KalkanCrypt сообщают размер фиксированного блока и оставляют после терминатора неопределённые байты.

`ErrInvalidInput` может означать неверный вход вызывающего кода или некорректные данные, возвращённые нативной библиотекой, включая ошибки разбора сертификатов.

`KeyStore.Password` и `Proxy.Password` имеют тип `string`. Пакет не может обнулить память Go, состояние KalkanCrypt и внутренние копии SDK.

## CMS и подписание хеша

По умолчанию CMS возвращается как DER. Для текстового вывода используйте `CMSOutputBase64` или `CMSOutputPEM`.

`GetTimeFromSig` читает штамп времени подписанта 0 (первого подписанта). Метод низкого уровня `ckalkan.Client.GetTimeFromSig` принимает явный индекс подписанта.

`GetCertFromCMS` возвращает встроенные сертификаты подписантов, используя индексы сертификатов SDK с единицы. В отличие от `VerifyCMS`, эта операция SDK принимает только содержимое контейнера: метод корневого пакета один раз читает `File` в память и применяет `WithMaxInputSize` во время чтения. Извлечение сертификатов не проверяет подпись.

`SignHashRequest.Digest` содержит заранее вычисленный дайджест. `DigestAlgorithm` описывает алгоритм его вычисления; нулевое значение поля равно `SHA256`. Обёртка проверяет алгоритм и длину дайджеста, но это поле не выбирает нативный алгоритм подписи. Дайджест должен соответствовать загруженному ключу: например, для тестовых ключей ГОСТ 2015 512 бит из репозитория используйте `GOST2015_512`. Linux SDK 2.0.13 определяет алгоритм по ключу и игнорирует флаги `Hash*` в `SignHash`. Неверный дайджест может иметь ожидаемую длину, и создание CMS всё равно завершится успешно; проверяйте полученный CMS на исходных данных.

## XML и WS-Security

`VerifyXML` передаёт криптографическую проверку в KalkanCrypt. Для SOAP 1.1 и SOAP 1.2 обязателен `ExpectedBodyID`; до нативного вызова проверяются:

- ровно один `ds:Signature`
- ровно один `ds:SignedInfo`, являющийся непосредственным дочерним элементом подписи
- ровно один SOAP Body, являющийся непосредственным дочерним элементом Envelope и имеющий точное ожидаемое значение `wsu:Id`, без удаления пробельных символов
- прямая `ds:Reference` на `#ExpectedBodyID`
- у Body reference либо нет `ds:Transforms`, либо есть ровно один непосредственный `ds:Transform` с Exclusive XML Canonicalization (`http://www.w3.org/2001/10/xml-exc-c14n#`)
- этот transform может содержать один параметр `InclusiveNamespaces` с атрибутом `PrefixList`; пустой список разрешён
- отсутствие дублирующих атрибутов `Id`, `ID` или `id` с ожидаемым значением в любом пространстве имён; объявления пространств имён не учитываются

Операции XML принимают `kalkan.Bytes`; файловые и предварительно закодированные источники отклоняются.

`GetCertFromXML` возвращает по одному встроенному сертификату на подпись в порядке документа. Если Java встречает несколько встроенных сертификатов, подписант определяется проверкой `SignatureValue` над `SignedInfo` каждым кандидатом; отсутствие или неоднозначность совпадения приводят к ошибке. Извлечение не проверяет данные по ссылкам, сроки и доверие сертификатам. Нативный бэкенд при извлечении не проверяет подписи. Чтобы устранить неоднозначный поиск нативного SDK по позиции или `Signature Id`, извлечение использует копию без неквалифицированных атрибутов `Id` у `ds:Signature`. Исходный XML не изменяется, и эта копия никогда не используется в `VerifyXML`.

Дополнительные прямые `ds:Reference` могут покрывать другие элементы WS-Security. SOAP должен быть в UTF-8; допускается один BOM в начале, при этом байты для нативной проверки подписи сохраняются. Для XML вне SOAP также допускается объявленная ASCII-совместимая кодировка, если пролог и корневой тег записаны в ASCII.

Для нативного бэкенда wrapper не применяет собственную allowlist-политику к `CanonicalizationMethod`, `DigestMethod` и `SignatureMethod`: набор поддерживаемых криптографических алгоритмов зависит от установленной версии KalkanCrypt, а fixtures репозитория не задают стабильного полного списка. Отклонение неподдерживаемых методов остаётся ответственностью KalkanCrypt.

## Проверка сертификатов

`TrustedCertificate.Type` проверяется и для `Path`, и для `Data`, но роль CA/intermediate/user передаётся в SDK только при использовании `Path`. API загрузки из буфера получает `Data` и `Format` и не имеет параметра роли.

`ValidateCertificateRequest.Mode` должен быть `CertificateValidationOCSP`, `CertificateValidationCRL` или `CertificateValidationNone`. Нулевое значение недопустимо. `CertificateValidationNone` явно отключает внешнюю проверку отзыва.

`CertificateValidation.OCSPResponse` равен `nil`, если `ReturnOCSPResponse` не запрошен.

Входной сертификат поддерживает DER, PEM и base64; `kalkan.File` отклоняется. PEM должен содержать ровно один блок `CERTIFICATE`. Явные DER, PEM и base64 преобразуются в PEM для нативного валидатора; raw и auto передаются без преобразования и должны уже иметь формат, принимаемый SDK. `RevocationSource` задаёт путь к CRL в CRL-режиме или переопределяет OCSP URL в OCSP-режиме.

`WithOCSPURL` и `WithTSAURL` переопределяют значения пакета по умолчанию. URL проверяется синтаксически, без ограничения адреса назначения.

`WithEndpointPolicy(EndpointPolicy{AllowedHosts: []string{"tsa.example", "ocsp.example"}, RequireHTTPS: true})` опционально ограничивает адреса из настроек и OCSP URL отдельных запросов. Укажите в `WithTSAURL` и `WithOCSPURL` адреса, разрешённые политикой. Имена узлов сопоставляются точно, без учёта регистра и завершающей точки DNS; `AllowedPorts` ограничивает порты (пустой список разрешает стандартные порты схемы), а IP-адреса требуют и `AllowIPAddresses`, и записи в разрешённом списке. Нарушения возвращают `ErrInvalidInput`. KalkanCrypt самостоятельно разрешает DNS и обрабатывает перенаправления; политика не заменяет ограничения исходящего сетевого доступа.

При включённой политике DNS-имена в `AllowedHosts` и URL должны быть записаны в ASCII. Для международных доменных имён используйте Punycode, например `xn--bcher-kva.example`; имена в Unicode отклоняются без автоматического преобразования IDNA. IPv6-адреса в `AllowedHosts` указываются без квадратных скобок, например `2001:db8::1`, а в URL — со скобками: `https://[2001:db8::1]/`. Идентификаторы зон IPv6 не поддерживаются.

Для выборочного чтения метаданных используйте `X509CertificateGetInfoFields`. `CertificateInfo` возвращает ИИН, БИН, тип субъекта и распознанные роли НУЦ при запросе соответствующих полей.

## ZIP-контейнеры

Java-бэкенд реализует `SignZIP`, `VerifyZIP` и `ExtractZIPSignerCertificate` в формате НУЦ: `META-INF/NCAManifest.xml` и отсоединённая CMS-подпись. Можно подписать обычный файл, дерево каталогов, список файлов через `|` по формату SDK или неподписанный ZIP. При подписании готового подписанного ZIP сначала проверяется контейнер, затем добавляется подписант CMS. Проверяются хеши всех файлов, все CMS-подписи, явное доверие, отзыв и присутствующие штампы времени. Контейнеры Java и оригинальной Linux-библиотеки KalkanCrypt 2.0.13 проверены в обе стороны.

Java обрабатывает ZIP и распакованные данные в памяти: максимум 64 MiB или меньший положительный `WithMaxInputSize`, до 4096 записей вместе с метаданными. Обход каталогов в путях, дубликаты имён без учёта регистра, символические ссылки и неподписанные лишние файлы отклоняются. Локальные заголовки должны соответствовать центральному каталогу; локальные записи вне каталога и добавленные перед архивом данные или исполняемый код отклоняются. Новые контейнеры используют SHA-256 для хешей файлов; проверка также поддерживает нативные URI ГОСТ95 и ГОСТ2015-512. Пустые контейнеры, другие форматы манифеста и несколько независимых ссылок на CMS не поддерживаются. Java создаёт выходной файл эксклюзивно; `WithAtomicZIPOutput()` дополнительно откладывает публикацию до завершения записи. При извлечении сертификата используется нумерация `SignerID` от 1.

`SignZIPRequest.OutputPath` должен оканчиваться на `.zip` без учёта регистра. До нативного вызова проверяется отсутствие файла как по исходному, так и по нормализованному пути. Нативный KalkanCrypt создаёт выходной файл без атомарной гарантии эксклюзивного создания.

`WithAtomicZIPOutput()` включает атомарную публикацию готового ZIP без замены существующего файла. KalkanCrypt пишет в закрытый временный каталог рядом с выходным файлом; временные файлы удаляются при завершении операции. Опция требует поддержки жёстких ссылок и контроля приложения над выходным каталогом. По умолчанию она отключена.

Входные пути ZIP передаются после проверки на пустое значение и NUL. Не изменяйте файлы до завершения операции.

`VerifyZIP` и `ExtractZIPSignerCertificate` независимы. Извлечение сертификата не проверяет ZIP-подпись. Если нужны оба результата, сначала вызывайте `VerifyZIP`.

## Диагностика

`WithObserver(func(ctx context.Context, event kalkan.OperationObservation) { ... })` сообщает о попытках вызовов бэкенда, включая настройку при `Open` и завершающий `Close`. `QueueWait`, `NativeDuration` и `TotalDuration` измеряют участок вызова: валидация до него и диагностические callbacks не учитываются. `NativeDuration` включает проверки и ожидание блокировок внутри callback бэкенда. `ErrorClass`, `NativeCode` и `Expected` описывают результат без исходного текста ошибок и входных/выходных данных. Возвращаемые ошибки сохраняются. Завершение перебора сертификатов и отсутствие необязательных свойств сохраняют ожидаемый статус.

Наблюдатели вызываются синхронно после освобождения очереди вызовов клиента, могут работать параллельно и не должны вызывать panic. Медленный наблюдатель задерживает вызывающую операцию; `Close` публикует сохранённый результат до диагностики и может вернуться раньше. `WithLogger` записывает те же безопасные метаданные без исходных сообщений SDK, путей, URL и полезной нагрузки. Если логгер и наблюдатель отсутствуют, время не измеряется.

## Проверки

```sh
make check
```

Интеграционные тесты Java, в том числе на macOS:

```sh
kalkan_java_sdk="$PWD/../kcsdk/java"
KALKANCRYPT_JAVA_PROVIDER="$kalkan_java_sdk/knca_provider_jce_kalkan-0.7.5.jar" \
KALKANCRYPT_JAVA_XML_LIBRARIES="$kalkan_java_sdk/kalkancrypt-xmldsig-0.5.jar:$kalkan_java_sdk/xmlsec-3.0.6.jar:$kalkan_java_sdk/slf4j-api-2.0.9.jar" \
KALKANCRYPT_JAVA_EXECUTABLE=java \
go test -count=1 ./...
```

`KALKANCRYPT_JAVA_XML_LIBRARIES` включает XML/WS-Security тесты; без неё запускаются проверки одного провайдера. Разделитель путей — `:` на macOS/Linux и `;` на Windows. CI получает четыре JAR из приватного `skarm/kcsdk` и запускает тесты на macOS/Linux с JDK 17 и 26. Токен для checkout и поведение PR из форков описаны в [настройке тестов](.github/TESTING.md#running-checks).

Java-тесты проверяют выпуск и извлечение штампов, добавление подписантов CMS, XML/WS-Security, ZIP-контейнеры, свойства сертификатов, HTTP-прокси, историческую проверку сертификатов/CRL, хеши по эталонам нативной библиотеки, прикреплённые и отсоединённые CMS в DER/Base64/PEM, файловые и пустые входы, отклонение изменённых данных, подписание готового хеша, неверный пароль PKCS#12, сроки и доверие сертификатов, извлечение сертификата подписанта и существующие нативные CMS. Набор выполнен с провайдером 0.7.5 и JDK 17 и 26 на macOS ARM64. Для тестов двусторонней совместимости с работающей нативной библиотекой дополнительно нужен `KALKANCRYPT_LIBRARY` на поддерживаемой нативной платформе. Тесты, которым не задана переменная окружения для нужного бэкенда, пропускаются.

Проверки отзыва и штампов используют независимо созданные временные RSA-сертификаты, CMS, CRL, OCSP-ответы и локальные HTTP-серверы. Проверяются в том числе отзыв промежуточного УЦ и TSA, неизвестный статус, подмена издателя/nonce/подписи/хэша штампа, недоверенный TSA, устаревшие данные, отказ сервиса, ограничения URL и отмена сетевого запроса. Исторические CMS в репозитории содержат производственные штампы TSA: без соответствующего доверия они должны отклоняться. Для дополнительной полной проверки исходных файлов задайте `KALKANCRYPT_JAVA_TSA_CERTIFICATES` — каталог с публичными `root_gost_2022.cer` и `nca_gost_2022.cer` с [сайта НУЦ](https://pki.gov.kz/en/cert-en/). Производственные сертификаты в репозиторий не добавляются. Проверка основных подписей этих файлов отдельно выполняется на копии без неподписанного атрибута штампа.

```sh
KALKANCRYPT_LIBRARY=/opt/kalkan/lib/libkalkancryptwr-64.so \
KALKANCRYPT_SDK_ASSETS=./testdata \
LD_LIBRARY_PATH=/opt/kalkan/lib \
make test-native
```

`make docker-test` ожидает Linux-библиотеки SDK в `.local/kalkancrypt/lib/linux/`.

В Windows:

```powershell
$env:KALKANCRYPT_LIBRARY = "C:\KalkanCrypt\KalkanCrypt.dll"
go test ./...
```

Исторические тестовые материалы и их публичный тестовый пароль описаны в [`testdata/README.md`](testdata/README.md).
