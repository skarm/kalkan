# KalkanCrypt для Go

[English version](README.md)

Go-обёртка над KalkanCrypt. Корневой пакет предоставляет типизированный API поверх низкоуровневого `ckalkan`.

## Совместимость

- Go 1.26+
- `linux/amd64` с `CGO_ENABLED=1`
- `windows/amd64`

Нативные тесты CI выполняются с `libkalkancryptwr-64.so.2.0.13`. Описанное ниже поведение SDK проверено на этой версии.

`windows/386`, Linux с `CGO_ENABLED=0` и другие платформы компилируются с заглушкой драйвера и возвращают `ErrUnavailable`.

SDK доступен на [портале разработчиков НУЦ РК](https://pki.gov.kz/ru/developers/). `WithLibraryPath` принимает абсолютный путь к x64 `.so` или DLL.

## Установка

```sh
go get github.com/skarm/kalkan@latest
```

## Пакеты

- [`github.com/skarm/kalkan`](https://pkg.go.dev/github.com/skarm/kalkan): типизированный API для CMS, XML, WS-Security, хеширования, ZIP, сертификатов, OCSP/TSA, прокси и логирования
- [`github.com/skarm/kalkan/ckalkan`](https://pkg.go.dev/github.com/skarm/kalkan/ckalkan): ABI-уровень с нативными флагами, кодировками и настройками буферов
- [`github.com/skarm/kalkan/isolated`](isolated): отдельные локальные worker с независимыми сессиями SDK и отменой через завершение процесса

Используйте `ckalkan`, если нужной операции нет в корневом пакете. Также используйте его для собственного высокоуровневого слоя над KalkanCrypt: со своими типами запросов, валидацией, политикой буферов, логированием или преобразованием ошибок.

`ckalkan` близок к нативному API. Вызывающий код отвечает за нативные флаги, кодировки, размеры буферов и обработку статус-кодов; он также должен учитывать жизненный цикл клиента, ограничения ABI и необходимость изоляции процесса.

### Выходные буферы `ckalkan`

Параметры буферов `ckalkan` разделены по двум формам ABI:

- `WithListBufferSize` задаёт начальную аллокацию для `KC_GetTokens` и `KC_GetCertificatesList`; значение по умолчанию равно 1 MiB. В Linux SDK эти функции не получают ёмкость буфера в байтах, а `tk_count` и `cert_count` являются выходными счётчиками элементов. Опция управляет размером аллокации, но не ограничивает нативную запись.
- `WithBufferSize` задаёт общую начальную ёмкость для вызовов с выходным буфером, которым передаётся его размер. Поля ёмкости в запросе имеют приоритет над этой опцией. Без неё используются начальные размеры 32 байта для сырых хешей SHA-256, ГОСТ 34.11-95 и ГОСТ 34.11-2015-256; 64 байта для сырого ГОСТ 34.11-2015-512; 256 байт для вывода хеша в Base64/PEM при любом алгоритме; 128 байт для остальных сырых алгоритмов хеша; 4 KiB для метаданных, 8 KiB для сертификатов и 64 KiB для подписей и остальных выходных буферов. Для прикреплённого CMS учитываются размер входных данных в памяти или файла и консервативный запас на подпись; также учитывается расширение Base64 и PEM. Для подписанного XML/WSSE учитываются размер XML в памяти и тот же запас (`KC_IN_FILE` этими двумя вызовами SDK не поддерживается). Перед вызовом ёмкость записывается в выходной параметр длины. При `KCR_BUFFER_TOO_SMALL` обёртка увеличивает буфер и повторяет вызов.
- Каждый выходной буфер по умолчанию имеет жёсткий лимит 64 MiB (`ckalkan.DefaultMaxOutputBufferSize`). `WithMaxBufferSize(0)` восстанавливает безопасное значение по умолчанию; положительное значение осознанно задаёт меньший или больший лимит вплоть до максимума нативного C `int` — 2^31-1 байт. Отрицательное значение приводит к ошибке `ErrInvalidOutputBufferSize` из `New`. Если нативный код сообщает размер выше действующего лимита, обёртка до повторного вызова и аллокации чрезмерной ёмкости возвращает типизированную `OutputBufferLimitError` с названием операции, запрошенным размером и применённым лимитом.

В Linux для `ZipConVerify` нужна защитная аллокация 64 KiB: SDK может записать данные за пределами меньшей переданной ёмкости. Если явный жёсткий лимит меньше этого безопасного минимума, вызов завершается ошибкой до входа в нативную библиотеку.

SDK в Linux также может повредить выходные длины `VerifyData`, если буферы информации о проверке и сертификата подписанта слишком малы. До входа в SDK адаптер запрашивает как минимум проверенные размеры по умолчанию: 4 KiB для информации и 8 KiB для сертификата, в том числе для универсальной проверки. Обёртка повторяет вызов в пределах жёсткого лимита; недостаточный лимит приводит к `OutputBufferLimitError` без вызова нативного верификатора и без возврата частичных данных.

Положительные значения `WithBufferSize` и `WithListBufferSize` нормализуются до значения не менее 64 KiB. Положительное значение `WithMaxBufferSize` соблюдается точно до максимума ABI C `int`. Меньший жёсткий лимит может не позволить операции использовать обычную начальную ёмкость; значение 64 MiB по умолчанию является границей безопасности и доступности, а не указанием, что операция обычно должна использовать столько памяти.

Лимит аллокации также ограничивает повторный рост обёртки для `KC_GetTokens` и `KC_GetCertificatesList`, но не устраняет их отдельный ABI-риск: эти две функции не получают ёмкость в байтах, поэтому опция не способна ограничить даже первую нативную запись.

Формально успешный результат списка, который занял всю аллокацию без завершающего NUL, считается потенциально усечённым и повторяется с увеличенной аллокацией.

## Использование клиента

```go
import (
	"context"
	"errors"
	"os"

	"github.com/skarm/kalkan"
)

func hash(ctx context.Context) (digest *kalkan.Digest, err error) {
	client, err := kalkan.Open(ctx,
		kalkan.WithLibraryPath(os.Getenv("KALKANCRYPT_LIBRARY")),
	)
	if err != nil {
		return nil, err
	}
	defer func() {
		err = errors.Join(err, client.Close())
	}()

	return client.Hash(ctx, kalkan.HashRequest{
		Algorithm: kalkan.GOST2015_512,
		Data:      kalkan.Bytes([]byte("document payload")),
	})
}
```

По умолчанию `Open` настраивает production endpoints:

- TSA: `http://tsp.pki.gov.kz:80`
- OCSP: `http://ocsp.pki.gov.kz`

Соответствующие test endpoints:

- TSA: `http://test.pki.gov.kz/tsp/`
- OCSP: `http://test.pki.gov.kz/ocsp/`

Test endpoints задаются явно:

```go
client, err := kalkan.Open(ctx,
	kalkan.WithLibraryPath(os.Getenv("KALKANCRYPT_LIBRARY")),
	kalkan.WithTSAURL("http://test.pki.gov.kz/tsp/"),
	kalkan.WithOCSPURL("http://test.pki.gov.kz/ocsp/"),
)
```

`WithTSAURL` и `WithOCSPURL` настраиваются независимо. Для операций подписания нужен `LoadKeyStore`; примеры находятся в [`example_test.go`](example_test.go).

`Open` всегда настраивает непустой TSA URL; `WithTSAURL("")` недопустим. Поля `Timestamp` в `SignCMSRequest` и `SignHashRequest` запрашивают штампы времени независимо от этой настройки URL. Функция SDK `KC_TSASetUrl` не возвращает статус, поэтому успешная настройка или вызов `ckalkan.Client.SetTSAURL` не подтверждает принятие URL библиотекой и доступность TSA-сервера.

## Модель выполнения

Состояние KalkanCrypt глобально для процесса. Нативные вызовы сериализуются по отдельности. Последовательность `LoadKeyStore` и подписания не атомарна: между ними могут выполниться другие вызовы. При совместном использовании клиента с разными контейнерами ключей необходимо синхронизировать всю последовательность загрузки и подписания или использовать отдельные процессы.

Храните и передавайте указатели, возвращённые `Open` или `ckalkan.New`; не копируйте структуры клиентов. `go vet` обнаруживает случайное копирование, в том числе низкоуровневого `ckalkan.Client`.

После успешного нативного `LoadKeyStore` клиент повторно загружает все сертификаты, успешно загруженные через `WithTrustedCertificate` или `LoadTrustedCertificate`, до допуска следующей операции. Байты сертификатов копируются после первой загрузки и хранятся до `Close`; файлы сертификатов должны оставаться доступными и неизменными для последующих загрузок контейнера. Восстановление завершается даже при отмене контекста после начала нативной загрузки контейнера. Ошибка восстановления сообщает о частичном успехе: контейнер уже сменился, доверие может быть неполным, а следующий `LoadKeyStore` повторит восстановление. Смена контейнера не откатывается.

`context.Context` может отменить ожидание гейта корневого клиента. Он не прерывает ожидание процессного мьютекса низкого уровня, загрузку библиотеки и уже начавшийся вызов KalkanCrypt, включая `Init`. Освобождение ресурсов после неудачного или отменённого `Open` также выполняется без отменяемого ожидания.

`Client.Close()` ждёт активный вызов и может заблокироваться навсегда. `Client.CloseContext(ctx)` прекращает ожидание вызывающего кода по `ctx.Err()`, оставляет клиент в состоянии `closing` и отклоняет новые операции. Жёсткие дедлайны требуют изоляции процесса. Закрытие начинается даже с уже отменённым контекстом. После завершения повторные вызовы возвращают сохранённый результат.

В Windows `LoadLibraryExW` вызывается с `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`. Текущий рабочий каталог и `PATH` исключены. Узкие `char*` аргументы передаются как UTF-8 с завершающим NUL.

## Опциональная изоляция процесса

Импортируйте `github.com/skarm/kalkan/isolated`, чтобы каждый клиент работал в отдельном дочернем процессе. Приложение само предоставляет режим worker в своём исполняемом файле; отдельная команда и сборка worker не нужны. Обычный `kalkan.Open` сохраняет выполнение в текущем процессе.

В начале `main`, до разбора аргументов приложения и запуска сервисов:

```go
if len(os.Args) == 2 && os.Args[1] == "--kalkan-worker" {
	if err := isolated.RunWorker(context.Background()); err != nil {
		os.Exit(1)
	}
	os.Exit(0)
}
```

Родитель запускает копию собственного исполняемого файла. `WorkerArgs` выбирает ветку выше и передаётся напрямую, без shell. Не запускайте сервисы в `init`: эти функции выполнятся и в дочернем процессе. `RunWorker` перенаправляет стандартные потоки в null; после его возврата нужно сразу завершить процесс, даже при успехе, поскольку нативный вызов ещё может висеть.

В обычной ветке выполнения приложения:

```go
executable, err := os.Executable()
if err != nil {
	return err
}
client, err := isolated.Open(ctx, isolated.Config{
	WorkerPath:  executable,
	WorkerArgs:  []string{"--kalkan-worker"},
	LibraryPath: "/opt/kalkan/libkalkancryptwr-64.so.2.0.13",
})
if err != nil {
	return err
}
defer client.CloseContext(ctx)

digest, err := client.Hash(ctx, kalkan.HashRequest{
	Algorithm: kalkan.SHA256,
	Data:      kalkan.Bytes([]byte("document payload")),
})
```

Один файл `.so`/DLL может использоваться несколькими worker: каждый процесс хранит свои ключи, доверие и изменяемое состояние SDK. Независимые клиенты работают параллельно; внутри общего клиента синхронизируйте составную последовательность загрузки ключа и подписания.

В [полных примерах](isolated/example_test.go) показаны SHA-256 хеширование файла и подпись CMS с проверкой. Каждый включает свою ветку worker, настройки, обработку ошибок и закрытие клиента. Для запуска перенесите нужную функцию в своё приложение как `main` (с `package main` и нужными импортами), измените пути к входному файлу и сертификатам, задайте `KALKANCRYPT_LIBRARY` и соберите приложение на поддерживаемой SDK платформе. Для подписания также задайте `KALKAN_KEY_PASSWORD` и используйте действующий сертификат с его цепочкой CA. Выходной CMS-файл не должен существовать. Отдельный исполняемый файл worker не нужен.

Пакет реализует все 21 операцию корневого клиента с существующими типами запросов и результатов. Настройки библиотеки передаются через `Config`, без сериализации замыканий `kalkan.Option`. `TSAURL` и `OCSPURL` — необязательные указатели: nil выбирает корневое значение по умолчанию. `Logger` и `Observer` выполняются в родителе.

Worker обменивается кадрами через два анонимных канала: бинарный заголовок и следующие за ним сырые блоки данных. Поля операций, настройки, ошибки и наблюдения имеют явный бинарный формат; байтовые входы и результаты передаются напрямую. `kalkan.File(path)` передаёт только путь; родитель не читает файл. Отправитель использует исходные срезы до возврата метода; при отмене он дожидается остановки своей горутины ввода-вывода. До загрузки SDK стандартные потоки перенаправляются в null, поэтому нативный stdout не повреждает ответы. TCP-сокет и токен не используются. Передача сохраняет байты, кодировки, явно пустые источники и произвольные байты строк. Ошибки сохраняют исходный текст и проверки `errors.Is` для sentinel-ошибок пакетов, контекста и `io/fs`. `kalkan.OCSPRevokedError`, нативные `ckalkan.KalkanError` и `ckalkan.OutputBufferLimitError` доступны через `errors.As`; `ckalkan.ErrorCodeOf` также работает. Другие конкретные типы ошибок не восстанавливаются.

`Open`, операции и `CloseContext` используют только переданный контекст, без внутренних тайм-аутов IPC. При включённом `Config.CustomOCSP` для Go OCSP в worker действует отдельный `OCSPTimeout`. Задавайте срок через `context.WithTimeout` или `context.WithDeadline` либо отменяйте контекст явно; без дедлайна ожидание может быть неограниченным. Контекст операции охватывает ожидание очереди и обмен с worker. Отмена контекста запуска после успешного `Open` не закрывает клиент. Отмена запроса в очереди сохраняет worker; отмена после начала отправки завершает его. Последующие вызовы возвращают `isolated.ErrWorkerFailed`, восстановление требует нового клиента. Автоматического повторения операций нет.

`Close()` ждёт активный вызов и штатное завершение worker без тайм-аута. Отмена любого ожидающего `CloseContext(ctx)` принудительно завершает worker и заканчивает общее закрытие с `ctx.Err()`, в том числе если другая горутина уже вызвала `Close()`. Конкурентные и повторные вызовы закрытия получают сохранённый результат; завершённый результат имеет приоритет над отменой контекста. Для каждого запущенного процесса выполняется ожидание завершения. Контекст не может прервать кодирование, декодирование и пользовательские callbacks в Go. Полученные нативные наблюдения вызываются после освобождения гейта, а наблюдения Close — после публикации результата закрытия, поэтому повторный вход допустим.

IPC не добавляет ограничения на размер сырых данных: длины кадров и блоков передаются 64-битными числами. Получатель читает данные частями ограниченного размера и объединяет их один раз после получения полного блока; маленькие блоки не требуют объединения. Обрезанный кадр не вызывает выделение памяти под весь заявленный размер. Операции по-прежнему принимают и возвращают целые срезы байтов, поэтому это не потоковый API к SDK. Метаданные ограничены 64 KiB, число блоков в кадре — 1024. Настройки входных и выходных лимитов и ограничения SDK продолжают действовать; это не ограничение всей памяти процесса.

Изоляция разделяет память и сессии SDK; worker сохраняет доступ приложения к файловой системе, окружению и сети. Относительные пути используют рабочий каталог worker на момент запуска. Прерванная операция могла уже создать результат или обратиться к TSA. Принудительное завершение пропускает deferred cleanup, поэтому могут остаться выходные файлы или временные ZIP-каталоги; приложение управляет путями результатов и восстановлением. Пароли и IPC-данные копируются в памяти и не могут быть обнулены этим пакетом.

## Входы и лимиты

Операции используют значения `Source`:

- `kalkan.Bytes(data)`: непреобразованные байты в памяти для данных, XML или уже декодированного бинарного объекта; конкретная операция выбирает нативные флаги
- `kalkan.Base64(data)`: вход в памяти, уже содержащий Base64-текст; конструктор не кодирует `data`
- `kalkan.PEM(data)`: готовый PEM-блок; конструктор не создаёт PEM-оболочку
- `kalkan.DER(data)`: готовый DER-объект для явного выбора DER в CMS и операциях с сертификатами
- `kalkan.File(path)`: данные из файла; содержимое читает операция или нативный адаптер

Допустимые варианты зависят от операции.

Кодировка источника, отличная от `EncodingAuto`, имеет приоритет над полями кодировки запроса и значениями операции по умолчанию. `Bytes`, `Base64`, `PEM` и `DER` задают явную кодировку; `File` начинает с `EncodingAuto`. Например, `VerifyCMSRequest.Encoding: EncodingBase64` не заставит интерпретировать источник `Bytes` как Base64. Используйте `Base64(encoded)` или явно восстановите выбор кодировки из запроса через `Bytes(encoded).WithEncoding(EncodingAuto)`.

Конструкторы источников в памяти не копируют и не преобразуют переданный срез. Валидация конкретной операции может декодировать PEM или Base64 до нативного вызова. На Linux и Windows входы в памяти с явной длиной обычно передаются в KalkanCrypt напрямую, без копирования в адаптере. Для данных и существующих CMS-подписей `SignData` в Base64, а также CMS-подписей `VerifyData`, `GetCertFromCMS` и `GetTimeFromSig` в Base64 создаётся отдельная копия с завершающим NUL: Linux SDK читает эти входы как C-строки, несмотря на аргумент длины. Передаваемая SDK логическая длина не меняется. Перед чтением или передачей в SDK путь проверяется на пустое значение и встроенные NUL-байты. Не изменяйте заимствованные срезы и файлы до завершения вызова.

`WithMaxInputSize` ограничивает входы в памяти на уровне корневого API и файлы, читаемые `GetCertFromCMS` и `GetTimeFromSig`. Ограничение не распространяется на файлы, которые SDK читает напрямую, и нативные выходные буферы. Для нативных выходных буферов по умолчанию действует жёсткий лимит 64 MiB (`kalkan.DefaultMaxOutputBufferSize`). `WithMaxOutputBufferSize(0)` восстанавливает это значение; положительное значение задаёт меньший или больший лимит (до максимума нативного C `int`), а отрицательное приводит к `ErrInvalidInput` из `Open`. Опция передаётся в `ckalkan.WithMaxBufferSize`. При превышении действующего лимита до чрезмерного повторного вызова или выделения памяти возвращается `ckalkan.OutputBufferLimitError`.

Бинарные результаты возвращаются строго по сообщённому SDK значению `outLen`; нулевые байты внутри этой длины сохраняются. У возвращённого среза `len` и `cap` ограничены логическим результатом, поэтому неиспользованная ёмкость буфера наружу не видна. Результаты-срезы являются ограниченными представлениями, а не копиями: пока результат используется, в памяти остаётся успешная исходная аллокация, зато не создаются вторая большая аллокация и копия. Известные текстовые результаты обрабатываются как C-строки и заканчиваются на первом NUL: некоторые методы KalkanCrypt сообщают размер фиксированного блока и оставляют после терминатора неопределённые байты.

`ErrInvalidInput` может означать неверный вход вызывающего кода или некорректные данные, возвращённые нативной библиотекой, включая ошибки разбора сертификатов.

`KeyStore.Password` и `Proxy.Password` имеют тип `string`. Пакет не может обнулить память Go, состояние KalkanCrypt и внутренние копии SDK.

## CMS и подписание хеша

По умолчанию CMS возвращается как DER. Для текстового вывода используйте `CMSOutputBase64` или `CMSOutputPEM`.

При присоединённом подписании SDK воспринимает существующую CMS с кодировкой DER, PEM или Base64 как запрос на добавление подписанта. Чтобы подписать байты CMS как самостоятельные данные, используйте raw-источник `Bytes` или файл с raw-кодировкой. На уровне `ckalkan` метод `SignData` использует `InBase64` для данных и существующей CMS-подписи; `In2Base64` относится к исходным данным в `VerifyData`.

Linux SDK ненадёжно проверяет CMS с пустыми данными. Для присоединённой CMS он может сообщить успех даже после изменения подписи, одновременно вернув отрицательную выходную длину, которую эта обёртка отклоняет. Проверка отделённой подписи возвращает `ckalkan.ErrorVerifyNoData`, в том числе для корректной подписи пустых данных. Обёртка сохраняет эти ошибки.

`GetTimeFromSig` читает штамп времени подписанта 0 (первого подписанта). Метод низкого уровня `ckalkan.Client.GetTimeFromSig` принимает явный индекс подписанта. Метод корневого пакета читает `File` в память и применяет `WithMaxInputSize`, поскольку операция SDK принимает содержимое CMS, а не путь.

Извлечение времени не проверяет подпись CMS или TSA. Linux SDK возвращает встроенное время даже после изменения подписи TSA. Прежде чем доверять времени, необходим успешный `VerifyCMS` с исходными данными для отделённой подписи.

`GetCertFromCMS` возвращает встроенные сертификаты подписантов, используя индексы сертификатов SDK с единицы. В отличие от `VerifyCMS`, эта операция SDK принимает только содержимое контейнера: метод корневого пакета один раз читает `File` в память и применяет `WithMaxInputSize` во время чтения. Извлечение сертификатов не проверяет подпись.

`SignHashRequest.Digest` содержит заранее вычисленный дайджест. `DigestAlgorithm` описывает алгоритм его вычисления; нулевое значение поля равно `SHA256`. Обёртка проверяет алгоритм и длину дайджеста, но это поле не выбирает нативный алгоритм подписи. Дайджест должен соответствовать загруженному ключу: например, для тестовых ключей ГОСТ 2015 512 бит из репозитория используйте `GOST2015_512`. Linux SDK определяет алгоритм по ключу и игнорирует флаги `Hash*` в `SignHash`. Неверный дайджест может иметь ожидаемую длину, и создание CMS всё равно завершится успешно; проверяйте полученный CMS на исходных данных.

## XML и WS-Security

`VerifyXML` передаёт криптографическую проверку в KalkanCrypt. Для SOAP 1.1 и SOAP 1.2 обязателен `ExpectedBodyID`; до нативного вызова проверяются:

- ровно один `ds:Signature`
- ровно один `ds:SignedInfo`, являющийся непосредственным дочерним элементом подписи
- ровно один SOAP Body, являющийся непосредственным дочерним элементом Envelope и имеющий точное ожидаемое значение `wsu:Id`, без удаления пробельных символов
- прямая `ds:Reference` на `#ExpectedBodyID`
- у Body reference либо нет `ds:Transforms`, либо есть ровно один непосредственный `ds:Transform` с Exclusive XML Canonicalization (`http://www.w3.org/2001/10/xml-exc-c14n#`)
- этот transform может содержать один параметр `InclusiveNamespaces` с атрибутом `PrefixList`; пустой список разрешён
- отсутствие дублирующих атрибутов `Id`, `ID` или `id` с ожидаемым значением в любом пространстве имён; объявления пространств имён не учитываются

Операции XML принимают `kalkan.Bytes`; файловые и предварительно закодированные источники отклоняются.

`GetCertFromXML` возвращает по одному встроенному сертификату на подпись в порядке документа; метод не проверяет подписи и доверие сертификатам. Чтобы устранить неоднозначный поиск SDK по позиции или `Signature Id`, извлечение использует копию без неквалифицированных атрибутов `Id` у `ds:Signature`. Исходный XML не изменяется, и эта копия никогда не используется в `VerifyXML`.

Дополнительные прямые `ds:Reference` могут покрывать другие элементы WS-Security. SOAP должен быть в UTF-8; допускается один BOM в начале, при этом байты для нативной проверки подписи сохраняются. Для XML вне SOAP также допускается объявленная ASCII-совместимая кодировка, если пролог и корневой тег записаны в ASCII.

Wrapper не применяет собственную allowlist-политику к `CanonicalizationMethod`, `DigestMethod` и `SignatureMethod`: набор поддерживаемых криптографических алгоритмов зависит от установленной версии KalkanCrypt, а fixtures репозитория не задают стабильного полного списка. Отклонение неподдерживаемых методов остаётся ответственностью KalkanCrypt.

## Проверка сертификатов

`TrustedCertificate.Type` проверяется и для `Path`, и для `Data`, но роль CA/intermediate/user передаётся в SDK только при использовании `Path`. API загрузки из буфера получает `Data` и `Format` и не имеет параметра роли.

`ValidateCertificateRequest.Mode` должен быть `CertificateValidationOCSP`, `CertificateValidationCRL` или `CertificateValidationNone`. Нулевое значение недопустимо. `CertificateValidationNone` явно отключает внешнюю проверку отзыва.

`CertificateValidation.OCSPResponse` равен `nil`, если `ReturnOCSPResponse` не запрошен.

По умолчанию режим OCSP использует KalkanCrypt. Для включения Go-реализации передайте `WithCustomOCSP()` в `Open`; для `isolated.Open` установите `Config.CustomOCSP: true`. В этом режиме нативная библиотека проверяет цепочку с `UseNothing`, а запрос OCSP и проверка подписи ответа выполняются в Go вне блокировки нативных вызовов. `WithOCSPTimeout` сам по себе не включает Go OCSP и не ограничивает нативные вызовы. При включённом Go OCSP он ограничивает весь HTTP-обмен, включая чтение тела: по умолчанию 15 секунд, ноль восстанавливает это значение, отрицательное значение недопустимо. Более короткий дедлайн или отмена контекста прерывает запрос. Ответ ограничен 1 МиБ; перенаправления запрещены. `WithProxy` и успешный `SetProxy` применяются и к Go OCSP; переменные окружения HTTP-прокси не используются.

Для Go OCSP нужен непосредственный издатель сертификата; нативный OCSP использует нативное хранилище сертификатов. Клиент ищет его среди сертификатов, загруженных через `WithTrustedCertificate` или `LoadTrustedCertificate`, проверяя имя и подпись. Если издатель известен только нативному хранилищу, передайте его через `ValidateCertificateRequest.Issuer` (DER, PEM или base64, без `File`). Это поле не добавляет доверия; нативная проверка цепочки обязательна. Без издателя возвращается ошибка, без перехода к нативному OCSP. Поле `Issuer` допустимо только при одновременно включённых `WithCustomOCSP()` и режиме OCSP.

Go OCSP проверяет статус переданного сертификата, а не отзыв каждого звена цепочки. Ответ должен быть подписан издателем либо его действующим делегированным OCSP-сертификатом; проверяются CertID, ResponderID, назначение ключа, критические расширения и свежесть. При отсутствии `nextUpdate` ответ принимается не дольше часа. Отзыв сертификата самого ответчика отдельно не проверяется. `CheckTime` относится к нативной проверке цепочки, а свежесть OCSP всегда проверяется на текущее время. Отзыв возвращает `*OCSPRevokedError` с временем отзыва; `ckalkan.ErrorCodeOf` сохраняет код `ErrorCertStatusRevoked`. Низкоуровневый `ckalkan.X509ValidateCertificate` по-прежнему предоставляет нативный OCSP без Go-таймаута.

Проверка подписей находится в `internal/certsig`: поддерживаются алгоритмы стандартной библиотеки и казахстанский ГОСТ 2015 (256 и 512 бит, каждый с соответствующим хешем Стрибог и казахстанским OID paramSetA). Открытые ключи должны иметь канонические координаты и принадлежать подгруппе простого порядка; кофактор 256-битной кривой равен 4. Параметры алгоритма подписи ГОСТ должны отсутствовать или быть NULL, а BIT STRING ключей и подписей должны содержать целое число байтов. Неожиданные ASN.1-поля в оболочках открытых ключей и сертификатов ГОСТ и структурах OCSP-ответов отклоняются. Неподдерживаемые алгоритмы, включая RSASSA-PSS в OCSP и прежние казахстанские ГОСТ 2004, отвергаются. Внешних Go-модулей нет, в том числе у тестов. Локальная часть взята из официального релиза [GoGOST](http://www.gogost.stargrave.org/) и распространяется под **GPL-3.0**: [источник и состав](internal/certsig/internal/gogost/README.md), [лицензия](internal/certsig/internal/gogost/LICENSE.md); лицензия MIT корневого проекта не заменяет эти условия.

Входной сертификат поддерживает DER, PEM и base64; `kalkan.File` отклоняется. PEM должен содержать ровно один блок `CERTIFICATE`. Явные DER, PEM и base64 преобразуются в PEM для нативного валидатора; raw и auto передаются без преобразования и должны уже иметь формат, принимаемый SDK. `RevocationSource` задаёт путь к CRL в CRL-режиме или переопределяет OCSP URL в OCSP-режиме.

`WithOCSPURL` и `WithTSAURL` переопределяют значения пакета по умолчанию. URL проверяется синтаксически, без ограничения адреса назначения.

`WithEndpointPolicy(EndpointPolicy{AllowedHosts: []string{"tsa.example", "ocsp.example"}, RequireHTTPS: true})` опционально ограничивает адреса из настроек и OCSP URL отдельных запросов. Укажите в `WithTSAURL` и `WithOCSPURL` адреса, разрешённые политикой. Имена узлов сопоставляются точно, без учёта регистра и завершающей точки DNS; `AllowedPorts` ограничивает порты (пустой список разрешает стандартные порты схемы), а IP-адреса требуют и `AllowIPAddresses`, и записи в разрешённом списке. Нарушения возвращают `ErrInvalidInput`. Опциональный Go OCSP запрещает перенаправления; нативные TSA и OCSP самостоятельно разрешают DNS и обрабатывают перенаправления. Политика не заменяет ограничения исходящего сетевого доступа и не защищает от DNS rebinding.

При включённой политике DNS-имена в `AllowedHosts` и URL должны быть записаны в ASCII. Для международных доменных имён используйте Punycode, например `xn--bcher-kva.example`; имена в Unicode отклоняются без автоматического преобразования IDNA. IPv6-адреса в `AllowedHosts` указываются без квадратных скобок, например `2001:db8::1`, а в URL — со скобками: `https://[2001:db8::1]/`. Идентификаторы зон IPv6 не поддерживаются.

Для выборочного чтения метаданных используйте `X509CertificateGetInfoFields`. `CertificateInfo` возвращает ИИН, БИН, тип субъекта и распознанные роли НУЦ при запросе соответствующих полей.

## ZIP-контейнеры

`SignZIPRequest.OutputPath` должен оканчиваться на `.zip` без учёта регистра. До нативного вызова проверяется отсутствие файла как по исходному, так и по нормализованному пути. KalkanCrypt создаёт выходной файл без атомарной гарантии эксклюзивного создания.

`WithAtomicZIPOutput()` включает атомарную публикацию готового ZIP без замены существующего файла. KalkanCrypt пишет в закрытый временный каталог рядом с выходным файлом; временные файлы удаляются при завершении операции. Опция требует поддержки жёстких ссылок и контроля приложения над выходным каталогом. По умолчанию она отключена.

Входные пути ZIP передаются после проверки на пустое значение и NUL. Не изменяйте файлы до завершения операции.

Нативный Linux-адаптер требует существующий каталог в качестве входа `SignZIP`. Для обычного файла, ссылки на файл, отсутствующего пути и других входов, не являющихся каталогом, он возвращает `ckalkan.ErrorParam` до создания ZIP. Это предотвращает ложный успех SDK с контейнером, в котором отсутствует исходный файл. Чтобы подписать один файл, поместите его в отдельный входной каталог и передайте этот каталог; выходной ZIP должен находиться за его пределами. Не меняйте входные пути и содержимое до завершения операции.

`VerifyZIP` и `ExtractZIPSignerCertificate` независимы. Извлечение сертификата не проверяет ZIP-подпись. Если нужны оба результата, сначала вызывайте `VerifyZIP`.

## Диагностика

`WithObserver(func(ctx context.Context, event kalkan.OperationObservation) { ... })` сообщает о попытках нативных вызовов, включая настройку при `Open` и завершающий `Close`. `QueueWait`, `NativeDuration` и `TotalDuration` измеряют участок вызова: валидация до него и диагностические callbacks не учитываются. `NativeDuration` включает проверки и ожидание блокировок внутри callback низкоуровневого вызова. `ErrorClass`, `NativeCode` и `Expected` описывают результат без исходного текста ошибок и входных/выходных данных. Возвращаемые ошибки сохраняются. Завершение перебора сертификатов и отсутствие необязательных свойств сохраняют ожидаемый статус.

Наблюдатели вызываются синхронно после освобождения очереди нативных вызовов, могут работать параллельно и не должны вызывать panic. Медленный наблюдатель задерживает вызывающую операцию; `Close` публикует сохранённый результат до диагностики и может вернуться раньше. `WithLogger` записывает те же безопасные метаданные без исходных сообщений SDK, путей, URL и полезной нагрузки. Если логгер и наблюдатель отсутствуют, время не измеряется.
